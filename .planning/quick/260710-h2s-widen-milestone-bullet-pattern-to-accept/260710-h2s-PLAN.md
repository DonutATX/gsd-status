<objective>
Widen `MILESTONE_BULLET_PATTERN` (src/parsers/roadmap.ts) so its checkbox
alternative accepts `[~]` and `[✅]`, matching the `[ xX~✅]` set `PHASE_BULLET`
already accepts. Today the checkbox alternative is `[ xX]`, so a milestone
bullet written `- [~] **v2.0 ...**` or `- [✅] **v1.0 ...**` fails the match and
its milestone is dropped from `data.milestones[]` (its phases fall through to
the synthetic "Other" bucket). PR #7 review flagged this asymmetry.

Purpose: Consistent marker acceptance between phase bullets and milestone
bullets in collapsed ROADMAPs.
Output: One-char-class regex widening, an accuracy pass on the two adjacent doc
comments, and a test pinning `[~]` and `[✅]` milestone bullets into
milestones[].

Scope note (read before implementing): `RoadmapMilestone` has NO `done` field.
Milestone "done" is DERIVED downstream in provider.ts (~line 206:
`element.phases.every(p => p.done)`), never from the bullet marker. The
milestone bullet marker is therefore an accept/reject filter only — it is never
consumed for done classification. So "[~] = not-done, [✅] = done" describes the
marker's general GSD meaning, but there is nothing to classify or store for
milestones. Do NOT add a `done` field to RoadmapMilestone — nothing consumes it
(YAGNI). The test asserts the bullets are PARSED (present in milestones[]),
exactly like the existing sibling tests for `🚧` and `[ ]`.
</objective>
